**Please note:** this release has had only limited testing: automated checks and one Android phone. The new way pictures are drawn and shown (on a thread of their own) has not been tried on a Windows, Linux or Mac computer, nor on any phone but that one. If something looks, plays or runs wrong, keep the previous version and send the game's report file (the newest file in the `logs` folder that starts with `report-`, or `ico-pc.log`) with a short description of what you saw.

## New

- Options > Gameplay > Yorda trips: running hand in hand for three seconds makes Yorda fall, as she does after the main gate opens. Off unless you turn it on.
- Options > Gameplay > Second memory card: ten more save slots on a second card; the game's own save and load screens offer both cards.
- Options > Extras > Back up your data and Restore from a backup, on the title screen (Windows, Linux, the Steam Deck, Mac and Android): your memory card, save states, settings and achievements in one `.zip` file you choose where to save, and put back from such a file, to keep a copy, move to another computer or phone, or go back to an earlier point. On Android this works even where the game's folder is hidden (Android 13 and later).
- Options > Language > Русский (bob-ttz): the subtitles and the game's menus in Russian, translated by bob-ttz. The game plays its English version underneath, so saves work with every language. Menu language also offers it.
- Options > Language > Русский (cobra838): a second Russian translation of the subtitles and menus, by cobra838. It works the same way as bob-ttz's, and Menu language offers it too.
- Options > Language > Português (Brasil) (ichagas7): the subtitles and the menus in Brazilian Portuguese, by Igor Chagas, with corrections by cobra838. It works the same way as the Russian translations, and Menu language offers it too.
- Options > Effects > Motion blur strength: a shorter trail than the PlayStation 2's if you find the blur too heavy, from 10 % to 100 %; 100 % is the original. It works with both Original and Smooth.
- The ending's credits now also name the translators, the contributors and the special thanks.
- On Windows and Android, save states now carry over to later versions when the part of the game they were saved in has not changed. When it has, loading the state tells you which version made it and why it cannot be resumed, instead of only saying it is from another version. A gameplay setting that a later version adds does not stop a state from carrying over while you leave that setting as it starts. Save states made by v0.9.7 or earlier cannot carry over.
- On a keyboard, F6 opens the Save states page. During play it pauses the game first, and pressed again on the page it takes you back to the game.
- The pictures are now drawn and shown on a thread of their own, so the game goes on with its next step while a picture is sent to the screen. The game still waits while a picture reads what that step changes, so the gain is smaller than a whole picture, and there is none at Frame rate Original. On phones it takes some of the work that held the sound back during play off the game, and can raise the frame rate where the graphics chip has time to spare. If a computer or phone shows problems with it, `render_thread = off` in the `[dev]` part of the settings file puts everything back on one thread.
- With Graphics API set to Vulkan (what phones normally use) or Direct3D 12, the pictures shown between the game's own frames are now sent to the graphics chip and put on the screen by a helper thread, so the next picture can be started while the one before is still being sent. With Vulkan on most phones and computers the whole next picture is drawn in that time; with Direct3D 12 and older Vulkan drivers only its first part is. The pictures are the same.
- On phones, the threads that draw the pictures and send them to the screen now keep to the phone's faster processor cores, and where a phone has one core faster than all the others, the game asks for that core for the thread that draws the pictures alone. Some phones say yes and still run the thread elsewhere: the game checks where the phone really lets it run, and then keeps it to the faster cores. `big_cores = false` in the `[dev]` part of the settings file leaves them where the phone puts them, if a phone shows problems with it.
- The game no longer repeats graphics commands that change nothing, so each picture takes less processor work with every Graphics API choice; `bind_cache = false` in the `[dev]` part of the settings file turns this off if a device shows problems with it.
- Each picture shown between the game's own frames now takes less processor work: what does not change from one picture to the next (how see-through each model is, where a character's joints turn, the pairing of the shadows' pieces, and a few checks the game made several times over) is worked out once and kept until it changes. This leaves more room for a second picture between two of the game's frames on phones. The pictures are the same.
- With Graphics API set to Direct3D 11, the game's 3D models are now prepared once per frame, as with the other Graphics API choices, so older graphics cards spend less time on each picture.
- At high resolutions (on phones at Resolution Auto or 2x), the pause menu's and the Options pages' words are drawn from letters prepared once instead of being worked out again for every pixel of every picture, so the menus take less of the graphics chip's time. They look exactly as before.
- On phones, the glowing outline around Yorda and the shadows (the aura) is worked out in two shorter steps instead of one long one per pixel, which takes less of the graphics chip's time; the picture is the same.
- On phones, the step that works out Yorda's and Ico's shadows reads less per pixel and no longer makes the graphics chip load and save a full-size picture that nothing looks at, so it takes less of the graphics chip's time; the picture is the same.
- The step that works out the shadows now reads its data four pixels at a time where the graphics chip can do that correctly (checked when the game starts), which takes less of the graphics chip's time, most of all on phones; the picture is the same.
- On phones, Yorda's and Ico's shadow shapes are now drawn inside the step that draws the scene instead of in a full-screen step of their own, so the graphics chip no longer saves the scene's depth and loads it back just for them, nor clears a full-size picture for them that nothing looks at; the picture is the same.
- On phones, a picture step that draws into only a part of the screen now has the graphics chip load and save only that part; the picture is the same. Most steps during play cover the whole screen, and those stay as they were.
- Every picture now skips a few steps that drew or saved nothing anyone looked at, which saves graphics time on phones; the picture is the same.
- On phones, in places where the light glows, and with some of the glowing outline's effects, the graphics chip no longer saves the picture's depth after the last step that uses it; the picture is the same.
- On phones, the glow around bright light is drawn with two or three fewer full-screen steps, so it takes less of the graphics chip's time; the picture is the same.
- Above the original resolution, the tiny gaps between parts of the world that the game fills in are now filled after the scene's see-through layers are drawn, instead of in the middle of the scene. On phones this takes most of the cost out of that step. Almost every filled pixel looks as before. Where a gap is now filled from its other side its colour can differ a lot: on one test picture a short line of 7 pixels along a seam changed by up to 109 levels (out of 255), up to 57 on the screen, and a few hundred other pixels by 1 or 2 levels; where light glows, about 1 % of the picture differs by up to 10 levels.
- On phones, filling those tiny gaps no longer takes a full-screen step of its own where Yorda's glowing outline (the aura) is drawn: it is done at the start of the step that draws the outline. Where light glows, it no longer brings back the two full-screen steps the glow saves. The picture is the same.
- The screen fades, the letterbox bars and the brightness setting are now applied while the finished picture is copied to the screen, instead of being drawn over it as extra full-screen layers. On phones this saves a full-screen step whenever nothing else is drawn over the picture, now also at the higher resolutions phones use, where the brightness setting cost that step in every frame of play and on the menus. It looks the same: measured within 2 levels of the old picture (out of 255), and within 1 level at the phone's own resolution.
- On graphics chips that can read the picture while drawing it (such as Adreno chips with the open Turnip driver, and many Mali chips), the game prepares several times fewer graphics pipelines at its first start and blends colours exactly as the PlayStation 2 did. Other chips, including PowerVR and Adreno with Qualcomm's own driver, draw as before.

## Fixed
- On Android, choosing the Enhanced preset no longer sets the Resolution to Auto, which lowered the picture's size on its own while the phone fell behind; the preset now uses the screen's size there as it does everywhere else, and Auto stays a choice you make in the Resolution row.
- On phones, the Frame rate counter sits inside the screen's safe area, so a rounded corner or a notch no longer cuts it off, whether the touch controls are showing, hidden, off or faded out for a gamepad.
- The pictures shown between the game's own frames are no longer held back whenever they might brush the next game step; they are held only when the step could not finish on time, so phones and PCs show more of them.
- With Vertical sync off and Frame rate at Uncapped, the pictures between the game's own frames are shown as fast as the graphics chip makes them, as Vertical sync off means on a PC, instead of being held to what the game expected the chip to manage. Only a picture that would make the game itself run late is left out.
- After the game itself ran late once (loading, saving a bug report, a slow moment of its own), or the pictures between its frames made it a fraction of a millisecond late, those pictures were held back to the old, stricter rule for most of the session, so phones showed about 30 pictures a second where they could show about 40. Now a tiny delay changes nothing, a larger one the pictures caused makes them a little more careful for a moment, and only repeated ones bring back the stricter rule, for a few seconds.
- On phones, most pictures between the game's own frames were still held back, about 30 a second where the graphics chip could make about 40: the game treated its short in-between step as if it did as much work as the step that works out the next frame. Each step is now judged by its own usual time, and a rare long step (a load, saving a bug report) no longer counts toward it.
- On phones, many pictures between the game's own frames were still held back, about 30 a second where the graphics chip could make nearly 40: the game planned each picture as if it would take as long as the slowest one lately. It now plans by how long a picture usually takes, and still holds the pictures back for a while after one runs late.
- On phones with Vertical sync off, most pictures between the game's own frames were still held back in some places, about 30 a second where the graphics chip could make 40 or more: when sending a picture to the screen took a few milliseconds, the game assumed the graphics chip could work on only one picture at a time. That wait now belongs to the helper thread that sends the pictures, and the chip keeps working on two.
- On phones with a 120 Hz screen, with Vertical sync on and Frame rate at 60 (the settings the game starts with), almost every picture between the game's own frames was held back whenever sending a picture to the screen took a few milliseconds, so the game showed about 30 pictures a second in places where it runs 30 frames. That wait belongs to the helper thread that sends the pictures and no longer holds them back, so a phone like the PowerVR one these settings were checked on should show about 50 to 60 a second there.
- A game step no longer waits behind the graphics chip. A picture shown between the game's own frames used to make the next game step wait while it waited for the graphics chip to finish an earlier picture, which on one phone added up to more than a second of every ten. The picture now does that wait before it starts, so a game step waits at most for the picture's own work, and it waits less often. Most of all on phones.

- The game kept writing the depth of every picture back to memory for the whole session after its first frame, which cost graphics time every picture, most of all on phones; it now does so only while a frame needs it. The setting that hands the picture's depth to an effects program such as ReShade, on unless you turn it off, also kept it doing so on every phone and on computers without such a program; it now does only while such a program is running.
- On Android, a save state made in an earlier session could not be loaded (the game closed). Save states made before you closed the app now load after you open it again.
- A save state's picture showed the pause menu and was small. It now shows the game as it was when you paused, larger and in its own shape, without the menu. A state saved right after loading another one gets the loaded state's picture.
- A wall could be seen through for an instant when the camera moved past it (with Frame rate above Original). The frames shown between the game's own frames no longer take the camera through a wall or a floor.
- Walking into the next area, the walls of the room you were leaving could change to the next area's look for an instant before the screen faded. The room now keeps its own look until the fade.
- On phones with a lot of memory, preparing the graphics at the first start stopped early, and the game then stuttered during play while it prepared the rest. It now finishes behind the progress bar before the game starts.
- On phones with a lot of memory the game no longer stops preparing its graphics early because of a cautious memory rule meant for one chip, and when it does stop it finishes quietly in the background instead of freezing for seconds on the first new room.
- With anti-aliasing, Downsampling, or a Resolution larger than the window, the game could stutter once when it first showed a picture; what it needs for that is now prepared at the first start with the rest of the graphics.
- On phones, entering some areas could freeze the game for up to two seconds the first time some models and floors were drawn there. What they need is now prepared at the first start with the rest of the graphics, which makes that first start a few seconds longer.
- From this version on, an update that does not change how the game draws keeps the graphics prepared before it, so its first start no longer prepares them all again. The first start of this version still prepares them once.
- Entering a new area, or loading a save, could make the game hitch while the new area's pictures were prepared: extra pictures shown between two of the game's frames made the game wait for them, most of all on phones whose graphics chip was still busy with the pictures before. The game now leaves such an extra picture out when it would hold up the game, or while the graphics chip or the screen is behind; every frame of the game is still shown. Where the graphics chip needs longer than one of the game's frames for a picture, the game can still slow down for a moment there.
