# config/data_members.pal.txt -- the ICO PAL retail ELF's data-only ico2000.a members.
#
# One row per (member, section) for every member that MAIN.MAP lists with
# .data/.rodata/.sdata but no .text, plus three runs in the same data-only
# territory that MAIN.MAP does not list (member name unmapped_<VMA>).
# Each member, typed by config/data_schema.pal.txt, is written as one C
# translation unit by tools/gen_data_c.py (build/pal/data/<member>.c, its rows the
# sections of that one object), which reads this table and the user's own
# baserom/pal/baseelf.elf; the bytes are never committed.
#
# Columns: <section> <member> <rom_lo> <rom_hi> <symbol>@<offset>,...
#   section   the section the bytes occupy in the retail ELF
#   rom_lo/hi VMA range [lo, hi) in baserom/pal/baseelf.elf (rom offset + 0x100000)
#   symbols   MAIN.MAP's names for the member, offset from rom_lo; "-" for none.
#             The three unmapped runs carry the derived name their C reader uses.
#
# Derivation. MAIN.MAP is a DIFFERENT, older link: no address below comes from
# it. It gives each member's order, size and symbols. The retail link loads the
# data-only members in the same passes and in the same (alphabetical, archive)
# order, so each run of them lies between two code-owning members whose ROM
# runs are fixed (the "group" comments). Inside a run every start is pinned by
# the matched C that reads the table from its base (an extern D_<VMA> or a
# symbol_addrs name, "C:"), by pointer words that target it, or by the chain
# (previous start + MAIN.MAP size, aligned, landing on the next pinned start).
# rom_hi is the next start, or the MAIN.MAP end when the ROM confirms that size
# with only zero alignment fill before the next start. Where the retail table
# is larger or smaller than MAIN.MAP's the row says so: those tables changed
# after the January link, and their exact end inside trailing zero fill is not
# recoverable (the bytes are identical either way).
