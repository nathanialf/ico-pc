# config/data_members.jpn.txt -- the ICO Japanese retail ELF's data-only ico2000.a members.
#
# One row per (member, section) for the same members as
# config/data_members.pal.txt: the 70 members MAIN.MAP lists with
# .data/.rodata/.sdata but no .text, plus the three unmapped runs (member name
# unmapped_<VMA>, the VMA being PAL's, kept as the member's name). Each member,
# typed by config/data_schema.jpn.txt, is written as one C translation unit by
# tools/gen_data_c.py (build/jpn/data/<member>.c, its rows the sections of that
# one object), which reads this table and the user's own
# baserom/jpn/baseelf.elf; the bytes are never committed.
#
# Columns: <section> <member> <rom_lo> <rom_hi> <symbol>@<offset>,...
#   section   the section the bytes occupy in the retail ELF
#   rom_lo/hi VMA range [lo, hi) in baserom/jpn/baseelf.elf (rom offset + 0x100000)
#   symbols   the PAL member's names (MAIN.MAP's, or the derived name its C
#             reader uses), offset from rom_lo
#
# Derivation. The Japanese disc ships no map or listing, and MAIN.MAP is a
# different, older link: no address below comes from either. The names are
# PAL's, carried by member order. Every start was found in this ELF:
#   1. Code. Each function the census (tools/correlate_elf.py) pairs with a
#      PAL function of the same length loads the same data the same way, so
#      a %hi/%lo pair or a $gp offset in the PAL function and the same
#      instruction in the twin give the PAL address and this ELF's address of
#      one datum. Every member's base read by code ("code:", the twin
#      functions that read it) is pinned this way, and so is the .data,
#      .rodata or .sdata of each code-owning neighbour.
#   2. Neighbours. Each run lies between two code-owning objects whose
#      sections are pinned by step 1; the group comments name them. A
#      member no code reads is bounded by the pinned members on each side.
#   3. Content. Each row was decoded with PAL's record type
#      (config/data_schema.pal.txt) and compared with PAL's member record by
#      record, pointer words compared as the address the PAL target has in
#      this link (functions by the census, data by step 1), strings by
#      content: "same" is equal record for record, "changed-content" is the
#      same layout with other values (ids into changed tables, text),
#      "layout-changed" is the same record type with rows added or removed,
#      "record-changed" is a record PAL's type does not hold. Every pointer
#      lands inside this ELF's image, every string is terminated and every
#      float field is finite, except in the two record-changed members.
# rom_hi is the next start, or the record count times the stride where zero
# fill for the next start's alignment follows (as in PAL's table). Where the
# span differs from PAL's the row says so and gives both row counts; the
# member is the same table with rows added or removed (the record stride and
# the zero fill after it fix the count exactly). The member order inside each
# run is PAL's, with two differences the code fixes: the unmapped run PAL
# places between game-param and motion-orient (hintTable) is first in the
# .data run here, and texture-path is in .rodata, between spider-def and
# way-group, where MAIN.MAP also puts it.
